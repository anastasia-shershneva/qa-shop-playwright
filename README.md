# QA Shop — Playwright и мониторинг

Решение тестового задания для позиции QA-инженера в «Профиль гостя».
Исходный магазин «Лавка» из архива работодателя находится в `qa-shop/`.
Код приложения сохранён без изменений. Автотесты, конфигурация запуска,
мониторинг и документация добавлены отдельно.

## Проверка локально

Нужны Node.js 20+ и npm. Рекомендуемая версия Node.js — 22.

```bash
npm ci --ignore-scripts
npm ci --ignore-scripts --prefix qa-shop
npx playwright install chromium
npm test
```

На Linux для первого запуска браузера используйте
`npx playwright install --with-deps chromium`.

Playwright сам запускает магазин на `http://127.0.0.1:3100`, создаёт отдельную
тестовую базу `.test-data/db.json` и сбрасывает её перед каждым сценарием.
Используется один worker, потому что база и эндпоинт сброса общие для всех сессий.
Уже работающий сервер на этом порту не переиспользуется.

```bash
npm run test:desktop       # только desktop Chromium
npm run report             # HTML-отчёт последнего прогона
npm run test:ui            # интерактивный режим
```

## Покрытие

33 сценария запускаются в двух проектах — desktop Chromium и мобильной
эмуляции Pixel 7, всего 66 проверок. Эмуляция проверяет мобильный viewport
и touch-режим Chromium, запуск на реальном телефоне не выполняется.

| Область | Проверки |
| --- | --- |
| Каталог | Исходный каталог, карточка, поиск по названию и описанию, регистр и пробелы, пустой результат, категории совместно с поиском, обе сортировки по цене, отсутствие товара и остатка |
| Корзина | Несколько товаров, количество и суммы, удаление, очистка, перезагрузка, превышение остатка |
| Промокоды | SALE10, WELCOME500 на границе 2000 ₽ и ниже неё, неизвестный код, отмена скидки |
| Заказ | Гостевой заказ, курьер и самовывоз, остаток, очистка корзины, бесплатная доставка от 3000 ₽, порог после скидки, ошибки полей, пустая корзина |
| Аккаунт | Регистрация, вход, выход, перезагрузка, невалидные поля, повторный email, неверный пароль, история и просмотр заказа |
| Дефекты | Нулевое количество, некорректный телефон, доступ к чужому заказу после смены аккаунта |

Основные покупательские сценарии выполняются через интерфейс. API используется
для начальной изоляции сессии, проверки остатков, подготовки промокода в сценарии
доставки и двух проверок на уровне сервиса. Подмены ответов сервера нет.
Тесты не используют фиксированные задержки. Состояния проверяются через
web-first assertions, завершение важных запросов ожидается явно.

Для сессии перед открытием страницы выполняется один запрос health через
`page.request`. Это задаёт cookie до трёх параллельных запросов инициализации
магазина. Первый визит без cookie таким способом не покрывается.

При ошибке сохраняются screenshot, trace и видео. Для BUG-01 и BUG-03
дополнительно прикладываются JSON-ответы. Отчёты доступны в
`playwright-report/` и `test-results/`. Персональные данные в сценариях вымышленные.

## Найденные дефекты

Подробные шаги, ожидаемые и фактические результаты приведены в
[BUGS.md](BUGS.md). На локальном исходном приложении через HTTP подтверждены
три дефекта. Они включены в набор как проверки ожидаемого корректного поведения.

В `known-defects.spec.js` используется `test.fail()` непосредственно перед
проверкой нарушенного требования. Эти проверки должны падать, пока дефекты
воспроизводятся, и отображаются в Playwright как expected failures. Ошибки
подготовки до этой отметки являются обычными сбоями. После исправления дефекта
Playwright выдаст unexpected pass, и отметку нужно убрать. Зелёный результат
пайплайна при expected failures не означает отсутствие дефектов магазина.

## Запуск против развёрнутого магазина

```bash
BASE_URL=https://shop.example.org npm test
```

В этом режиме Playwright не запускает локальный магазин и не вызывает
глобальный сброс данных. Создаются тестовые аккаунты и заказы, а остатки товаров
уменьшаются. Используйте отдельную тестовую установку с исходными остатками.
Повторные прогоны на одной установке могут исчерпать остаток. Перед очередным
полным прогоном восстановите данные тестовой установки.

## Магазин, Prometheus и Grafana

### Один контейнер для Render Free

Корневой `Dockerfile` объединяет магазин, Prometheus и Grafana за Nginx.
Это позволяет разместить тестовый стенд в одном бесплатном Web Service.
Исходный код магазина при этом не изменяется. Публичный магазин открывается
по корневому адресу сервиса, Grafana — по `/grafana/d/qa-shop/`.
Prometheus слушает только внутренний localhost контейнера.

В Render подключите этот публичный репозиторий как Web Service, выберите
Docker, ветку `main`, корневой Dockerfile и тариф Free. `render.yaml` содержит
эквивалентную конфигурацию для Blueprint. Адрес из `RENDER_EXTERNAL_URL`
используется для настройки ссылок Grafana. Пароль администратора берётся из
`GRAFANA_ADMIN_PASSWORD`, а при отсутствии генерируется на старте.

Бесплатный сервис засыпает после 15 минут без входящих запросов, поэтому
первый ответ может задержаться примерно на минуту. Файлы и данные метрик
эфемерные — при пересоздании контейнера база возвращается к исходному
состоянию. Это ограничение тестового стенда. Docker Compose ниже использует
постоянные volumes для сервера, где доступен постоянный диск.

В CI дополнительно собирается этот контейнер и проверяется с лимитом 512 МБ.
`node deploy/smoke.mjs` проверяет магазин, каталог, Grafana, дашборд,
сбор метрик и `/metrics`. Против публичного адреса проверка запускается так:

```bash
DEPLOY_URL=https://your-service.onrender.com node deploy/smoke.mjs
```

### Отдельные сервисы через Docker Compose

На сервере с Docker Engine и Compose создайте `.env` из примера, задайте
уникальный пароль администратора Grafana и её публичный URL.

```bash
cp .env.example .env
# Укажите GRAFANA_ADMIN_PASSWORD и GRAFANA_ROOT_URL в .env
docker compose up -d --build
docker compose ps
```

По умолчанию магазин доступен на порту 8080, Grafana — 3001.
Дашборд открывается по `/d/qa-shop/` в Grafana. Внешнему проверяющему доступен
просмотр дашборда без входа с ролью Viewer. Изменения требуют авторизации
администратора. Prometheus доступен только внутри сети Compose.
Перед публикацией настройте HTTPS через reverse proxy или HTTPS-хостинг.

Служебный сброс данных выключен в развёртывании Compose. Данные магазина,
метрик и Grafana сохраняются в отдельных Docker volumes. Команда
`docker compose down` останавливает сервисы с сохранением данных.

### Что показывает дашборд

- Доступность scrape магазина и скорость запросов.
- p95 времени ответа API и долю ответов 5xx.
- Число заказов и выручку за выбранный период.
- Неудачные входы и добавление товаров в корзину.
- Число сессий в памяти и товары без остатка.
- RSS-память процесса и p99 задержки event loop.

Prometheus собирает `/metrics` каждые 15 секунд. Для графиков скорости нужны
хотя бы две точки. Счётчики обрабатываются через `rate`/`increase`, поэтому
перезапуск процесса учитывается. `up` отражает доступность сбора метрик,
а число сессий не равно числу покупателей онлайн. Заказы и выручка относятся
к оформленным заказам, подтверждения платежей в магазине нет.

### Проверка мониторинга

1. Откройте `/api/health` и `/metrics` магазина.
2. В Grafana проверьте, что «Доступность сбора метрик» показывает 1.
3. Добавьте товар в корзину, оформите тестовый заказ и выполните вход с
   неверным паролем.
4. После двух интервалов сбора проверьте изменение соответствующих метрик.

## CI

GitHub Actions устанавливает зависимости и Chromium, запускает оба проекта
Playwright и сохраняет HTML-отчёт, trace, видео и JSON как artifact
`playwright-results` на 14 дней. Workflow запускается при push в `main`,
pull request и вручную через Actions.

## Использование ИИ

При подготовке тестов, конфигурации мониторинга и документации использован
ChatGPT/Codex, что разрешено условиями задания. Описанные дефекты проверяются
на исходном приложении. Фактический результат каждого прогона следует смотреть
в Playwright-отчёте и GitHub Actions.

## Статус сдачи

Публичные адреса магазина и Grafana будут добавлены после развёртывания
и проверки доступности из интернета. Локальный запуск и конфигурация Compose
сами по себе не подтверждают выполнение этого пункта задания.
