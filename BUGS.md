# Дефекты исходного qa-shop

Среда первичной проверки — исходный архив работодателя, Node.js 22.22.0,
локальный HTTP-сервер. Дефекты подтверждены запросами к работающему приложению
23.11.2026. Для повторения используются только вымышленные данные.

## BUG-01. API добавляет одну единицу товара при qty=0

Приоритет P2, серьёзность Minor. Воспроизведение —
`tests/known-defects.spec.js`, BUG-01.

Предусловие — пустая корзина, товар 1 есть в наличии.

1. Отправить `POST /api/cart/items` с JSON `{"productId":1,"qty":0}`.
2. Проверить ответ и `GET /api/cart` в той же сессии.

Ожидается HTTP 400, количество товаров в корзине остаётся 0.

Фактически HTTP 201, в корзину добавлена одна единица товара. Аналогичное
поведение можно получить через карточку, вручную установив количество 0.
В `server.js` значение 0 заменяется на 1 до валидации выражением `qty || 1`.

## BUG-02. Заказ оформляется с телефоном из двух цифр и девяти пробелов

Приоритет P2, серьёзность Major. Воспроизведение —
`tests/known-defects.spec.js`, BUG-02.

Предусловие — в корзине есть товар.

1. Перейти к оформлению заказа, указать имя и выбрать самовывоз.
2. Ввести телефон `1         1` — две цифры с девятью пробелами между ними.
3. Подтвердить заказ.

Ожидается ошибка поля телефона, заказ не создаётся, остаток не меняется.

Фактически заказ создаётся с HTTP 201, отображается подтверждение, остаток
уменьшается. Такой телефон не позволяет связаться с покупателем.
Текущая регулярная проверка ограничивает длину строки, но не число цифр.

## BUG-03. Второй аккаунт получает данные заказа первого в той же сессии

Приоритет P1, серьёзность Critical. Воспроизведение —
`tests/known-defects.spec.js`, BUG-03.

1. Зарегистрировать аккаунт A.
2. Оформить курьерский заказ с тестовыми именем, адресом и телефоном.
3. Сохранить ID заказа.
4. Выйти из аккаунта A.
5. В том же браузерном контексте зарегистрировать другой аккаунт B.
6. Убедиться через `/api/auth/me`, что ID текущего пользователя отличается от A.
7. Открыть `/api/orders/{id}` с ID заказа A или страницу `/#/order/{id}`.

Ожидается HTTP 404 либо 403, сведения о заказе A недоступны аккаунту B.

Фактически HTTP 200, ответ содержит заказ A, включая имя, телефон и адрес.
При проверке получен `userId=1` в заказе при `id=2` у текущего пользователя.
`sid` сохраняется при выходе, а доступ к заказу разрешается по совпадению
пользователя **или** старого sid. Это позволяет читать чужие персональные
данные при смене аккаунта на общем устройстве. Воспроизведение не предполагает
доступ к заказам произвольного пользователя из независимой сессии.
